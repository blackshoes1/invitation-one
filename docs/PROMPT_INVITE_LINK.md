# 개발 프롬프트 — 개인 초대 링크의 목적 정렬

작성: 2026-09-06 · 예식 2026-10-18 (42일 전)

> **후속(2026-09-06): 핵심 제약은 해소됐다.** 아래 "정정" 절에서 지적한
> "초대 토큰을 주려면 반드시 그룹에 속해야 한다"는 제약을
> `20260906000200_groupless_invites.sql` 로 풀었다 (`group_members.group_id`
> nullable). 어드민 → 그룹 탭 → **개별 초대**에서 그룹 없이 이름·연락처를
> 등록하고 개인 링크를 발급한다. 이 문서의 나머지(격차 A·B, 결정 항목)는
> 그대로 유효하다.

## 목적 (요청자 원문)

> 1. 그룹 내 개인 링크 생성 (이름, 전화번호 자동 입력을 위함)
> 2. 개인이 링크로 진입 시 이름 보임. 그룹 정보(그룹명, 참석자) 보임.

---

## 먼저: 이미 되어 있는 것 (다시 만들지 말 것)

목적 1·2 는 **그룹 링크에서는 이미 동작한다.** 새로 만들 게 아니라 정렬할 문제다.

| 목적 | 현재 | 근거 |
|---|---|---|
| 사람별 링크 발급 | ✅ | `POST /api/admin/groups/<id>/members/invite` — 토큰 1개로 **두 주소**를 함께 반환 (`url` 그룹용 / `personalUrl` 개인용). 어드민 명단에 사람별 버튼 + "전체 개인 링크 복사" |
| 이름 자동 입력 | ✅ | `?i=` 진입 시 `GET /api/delivery/invite` → `{ name, phoneMasked, groupSlug }` 로 폼 프리필 |
| 전화번호 자동 입력 | ✅ | 실제 번호는 브라우저로 내려가지 않는다. 마스킹(`010-****-1234`)만 보이고 제출 시 서버 RPC 가 토큰 해시로 채움 |
| 진입 시 이름 보임 | ✅ | 두 링크 모두 |
| 그룹명 보임 | ⚠️ **그룹 링크만** | `/delivery/group/<slug>` 는 `<h1>` 에 그룹명. `/delivery?i=` 는 그룹을 아예 안 보여준다 |
| 참석자 보임 | ⚠️ **부분** | 그룹 링크는 `OrderList` 로 **주문한 사람**을 보여준다. **명단(아직 신청 안 한 사람)은 하객에게 안 보인다** |

관련 파일: `src/lib/invite.ts`, `src/app/api/admin/groups/[id]/members/invite/route.ts`,
`src/components/admin/GroupsTab.tsx`, `src/app/delivery/page.tsx`,
`src/app/delivery/group/[groupId]/page.tsx`, `src/components/delivery/useInvite.ts`

## 그래서 실제 격차는 두 개다

### 격차 A — 개인 링크(`/delivery?i=`)에는 그룹 정보가 없다

의도된 설계다. 개인 링크는 **그룹에 묶이지 않는 본인 주문**을 위한 것이고,
`src/lib/orderKind.ts` 가 "그룹 페이지가 아니면 개인 주문"으로 판정한다.
그런데 목적 2 는 "링크로 진입하면 그룹 정보가 보여야 한다"고 말한다.
**두 링크의 역할이 목적과 어긋난다.**

### 격차 B — "참석자"의 뜻이 정해져 있지 않다

두 해석이 가능하고, 개인정보 노출 범위가 다르다.

- **(가) 이미 주문한 사람** — 지금 `OrderList` 가 보여주는 것. 자기가 이름을
  남겼으니 노출에 동의한 셈이다
- **(나) 명단 전체** (예: "우리 모임 12명 중 5명 신청") — 아직 신청도 안 한
  사람의 이름이 다른 하객에게 보인다. 관리자가 명단에 넣은 것뿐이라
  **동의한 적이 없다**

## 결정이 필요한 것 (작업 전에 물어볼 것)

1. **개인 링크를 계속 쓸 것인가?**
   - (A) **그룹 링크만 발송한다** → 개인 링크는 어드민에서 숨기거나 제거.
     ⚠️ 아래 "정정" 참고 — 그룹에 속하지 않은 개별 지인에게는 답이 되지 않는다
   - (B) **개인 링크에도 그룹 정보를 보여준다** → 주문은 개인으로 유지하되
     "○○ 모임 · 현재 N명 신청" 배너를 추가. 코드가 늘고, "그룹 정보가
     보이는데 왜 그룹 주문이 아닌가"라는 혼동이 새로 생긴다
   - (C) 지금 그대로 둔다 (개인 링크 = 그룹 정보 없음)

2. **"참석자"는 (가)인가 (나)인가?**
   (나)라면 이름을 그대로 쓸지, `_mask_name()`(이미 있음)으로 가릴지도 함께.

3. **명단 연락처가 얼마나 채워져 있나?** 번호가 없으면 자동 입력이 안 되고
   링크의 이점이 절반이다. 아래 쿼리로 먼저 확인할 것.
   ```sql
   select count(*) 전체,
          count(*) filter (where phone is not null and phone <> '') 연락처보유,
          count(*) filter (where invite_token_hash is not null) 링크발급
   from group_members;
   ```

## 정정 — "그룹 링크만 발송"은 그룹에 속한 사람에게만 답이다

처음에 (A) 그룹 링크 일원화를 추천했는데, **그룹에 속하지 않은 개별 지인**을
빠뜨린 추천이었다. 확인한 사실은 이렇다.

- `group_members.group_id` 는 **`not null references groups(id)`** 다.
  즉 **초대 토큰을 발급하려면 반드시 어떤 그룹에 속해야 한다.**
  자동 입력(목적 1)을 주려면 명단에 넣는 것 말고 다른 길이 없다.
- 반대로 **그룹도 토큰도 없이 신청하는 길은 이미 열려 있다.** `/delivery` 는
  누구나 이름·연락처를 직접 입력해 주문할 수 있다. 자동 입력이 필요 없다면
  개인을 위해 그룹을 만들 이유가 없다.

### 개인들을 한 그룹에 몰아넣으면 안 되는 이유

"개인/지인" 같은 그룹 하나를 만들어 담는 건 가능하지만, **그 그룹 링크를
보내면 안 된다.** `get_group_orders(p_slug)` 가 그 그룹의 모든 주문과
**참여자 이름 배열(`member_names`)** 을 anon 에게 돌려준다. 서로 모르는
지인들끼리 이름·신청일이 보인다.

`/delivery?i=` (개인 링크)는 그룹 페이지를 거치지 않으므로 이 노출이 없다.
**개인 링크가 존재하는 이유가 바로 이것이다.**

### 그래서 정정된 추천: 두 링크를 다 유지한다

| 대상 | 보낼 링크 | 얻는 것 |
|---|---|---|
| 진짜 모임 (회사·동창·가족) | **그룹 링크** `/delivery/group/<slug>?i=` | 이름·번호 자동 입력 + 그룹명 + 신청 현황 |
| 개별 지인 (모임 없음) | **개인 링크** `/delivery?i=` | 이름·번호 자동 입력. 그룹 정보는 **안 보이는 게 맞다** |
| 명단에 없는 사람 | `/delivery` (토큰 없음) | 직접 입력. 그룹·토큰 불필요 |

목적 2의 "그룹 정보 보임"은 **그룹에 속한 사람에게만 해당하는 요구**였던 셈이다.
이 구분은 `src/lib/orderKind.ts` 가 이미 정확히 지원한다 — 같은 토큰이라도
개인 링크로 들어오면 개인 주문, 그룹 링크로 들어오면 그룹 주문이다.

### 운영상 남는 위험과 작은 보완

개별 지인을 담아둔 그룹의 **그룹 링크를 실수로 보내면** 위 노출이 일어난다.
어드민에서 그 그룹의 "그룹 링크 복사" 버튼을 아예 없애면 실수를 구조적으로 막는다.

- `groups` 에 `personal_only boolean not null default false` 추가 (추가 전용)
- 어드민 그룹 카드에 체크박스, 켜면 `GroupsTab` 에서 그룹 링크 복사 버튼과
  "링크 복사"(그룹 대표 링크)를 숨기고 개인 링크만 남긴다
- 서버는 막지 않아도 된다 — 링크 자체는 유효해야 이미 뿌린 것이 계속 동작한다.
  이건 **실수 방지**이지 접근 제어가 아니다

## 작업 (A안을 고른 경우 — 가장 짧은 경로)

1. **어드민에서 링크 종류를 하나로 줄인다.**
   `GroupsTab.tsx` 의 사람별 버튼 두 개(개인/그룹) → 그룹 링크 하나로.
   "전체 개인 링크 복사"도 그룹 링크로 바꾼다.
   `personalInviteUrl` 자체는 남겨둔다 — 이미 뿌린 링크가 있으면 계속 동작해야 한다.

2. **그룹 페이지의 첫인상을 목적에 맞춘다.**
   `?i=` 로 들어오면 상단에 "○○님, 반가워요 · **{그룹명}**" 을 보여주고,
   신청 현황을 눈에 띄게 올린다. 지금은 이름이 폼 안에서만 드러난다.

3. **연락처 확인 UX 를 명시한다.**
   마스킹 번호 옆에 "이 번호로 연락드릴게요 · 다른 번호 쓰기"가 이미 있다.
   문구만 목적에 맞게 다듬는다.

4. **검증**
   - 유닛: 링크 생성 헬퍼 (`inviteUrl`)
   - E2E: 그룹 링크 진입 → 이름·그룹명·현황이 보인다 / 전체 번호는 HTML 어디에도
     없다(기존 `db-flows.spec.ts` 규칙 유지) / 이미 뿌린 개인 링크가 여전히 동작한다

## 작업 (B안을 고른 경우 — 추가분만)

1. `GET /api/delivery/invite` 응답에 그룹 표시 정보를 더한다
   (`groupName`, 그리고 (가)/(나) 결정에 따라 참석 현황). **연락처는 절대 추가하지 말 것** —
   마스킹만 내려가는 현재 계약을 깨면 안 된다.
2. `/delivery?i=` 상단에 그룹 배너. **"이 신청은 모임 주문에 합쳐지지 않아요"**
   를 함께 적어 격차 A 의 혼동을 막는다.
3. `orderKind.ts` 의 규칙은 **바꾸지 않는다** — 그룹 정보를 보여주는 것과
   그룹 주문으로 묶는 것은 별개다. 이 구분을 주석으로 못 박을 것.

## 지켜야 할 것 (이 저장소의 기존 계약)

- **실제 전화번호는 브라우저로 내려가지 않는다.** 초대 API 는 마스킹만 반환하고,
  실제 번호는 제출 시 서버 RPC 가 토큰 해시로 채운다. E2E 가 이걸 감시한다
  (`/010-\d{3,4}-\d{4}/` 가 HTML·응답에 나오면 실패)
- **DB 에는 토큰 해시(sha256)만 저장한다.** 재발급하면 이전 링크는 무효
- **주문 종류 판정은 `src/lib/orderKind.ts` 한 곳에서만.** 화면에 무엇을 보여주든
  종류는 진입 경로가 정한다 (`docs/GROUP_PERSONAL_ORDER.md`)
- **명단에서 사람을 지우면** 그 사람 주문의 `group_member_id` 가 `ON DELETE SET NULL`
  로 조용히 끊긴다. 명단 삭제 UI 를 건드린다면 이 점을 먼저 확인할 것
- 마이그레이션은 추가 전용·멱등 (`supabase/migrations/README.md`)
