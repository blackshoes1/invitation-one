# 개발 프롬프트 — 개인 링크 첫 화면을 "묻기"에서 "인사하기"로

작성: 2026-09-06 · 예식 2026-10-18

## 문제

개인 초대 링크(`/delivery?i=…`, `/delivery/group/<slug>?i=…`)로 들어오면 첫 화면이
**"받는 분 정보를 알려주세요 📋"** 다 (`src/components/delivery/form/StepContact.tsx`).

그런데 그 아래 이름 칸은 **이미 채워져 있고**, 연락처도 이미 확인된 상태로
마스킹 표시된다(`InvitePhoneBox` — "010-****-1234 · 초대 링크로 확인됨 ✓").

즉 **이미 아는 걸 알려달라고 묻는다.** 하객 입장에서는 어색하고, 자기 이름이 왜
거기 적혀 있는지 설명도 못 받는다. 초대 링크의 목적(다시 입력하는 번거로움을
없애는 것)이 첫인상에서부터 드러나지 않는다.

## 하고 싶은 것

이미 아는 정보이니 **입력을 요구하는 화면 대신, 이름을 불러주며 확인만 받는
화면**으로 바꾼다.

```
👋 근영님, 반가워요

청첩장을 직접 전해드릴게요.
아래 정보가 맞는지만 확인해 주세요.

┌──────────────────────────────┐
│ 성함      근영               │
│ 연락처    010-****-1234      │
│           초대 링크로 확인됨 ✓ │
└──────────────────────────────┘

[ 맞아요, 계속 ]   [ 정보 수정 ]
```

---

## 두 가지 방향 — A 를 추천

### A안 (추천) — 스텝 0 을 인사·확인 화면으로 **교체**

`StepContact` 가 초대 프리필이 있을 때만 다른 모습을 렌더한다. 스텝 개수·인덱스·
진행바·검증 흐름은 **그대로 둔다.**

- 프리필 있음 → 인사 + 확인 카드 + `[맞아요, 계속]` / `[정보 수정]`
- `[정보 수정]` → 지금의 입력 폼으로 전환 (이름 input + 번호 input)
- 프리필 없음 → **지금 화면 그대로** (변화 없음)

장점: 회귀 위험이 낮다. 스텝 인덱스를 건드리지 않으므로 `next()` 의 단계별 검증,
`StepIndicator`, 합석 제안 분기가 전부 그대로다. 마음에 안 들면 이 컴포넌트만 되돌리면 된다.

단점: 확인 탭 한 번은 여전히 남는다.

### B안 — 스텝 0 을 **건너뛰고** 배송지부터 시작

상단에 "근영님, 반가워요 — 연락처는 010-****-1234 로 받아둘게요 · 수정" 배너를 두고
첫 화면을 배송지로 만든다.

장점: 탭 한 번이 줄어든다.

단점: `TOTAL` 6 → 5 가 **조건부**가 되고, `content()` 의 `switch (step)` 인덱스,
`next()` 의 `if (step === N)` 검증, `StepIndicator` 의 `LABELS` 가 전부 초대 유무에 따라
어긋난다. 지금 구조에서 인덱스를 조건부로 바꾸면 조용한 버그가 나기 쉽다.

**42일 남은 시점에는 A안. B안은 예식 후 스텝 구조를 정리할 때.**

---

## 작업 (A안)

1. **`StepContact` 에 확인 모드 추가**
   - 새 prop: `inviteName?: string | null` (초대로 확인된 이름 — 있으면 확인 모드)
   - 내부 state 로 `editing` 을 두고, `[정보 수정]` 을 누르면 기존 입력 폼 렌더
   - 확인 모드에서는 `Q` 의 `title` 을 `` `${inviteName}님, 반가워요 👋` `` 로,
     `sub` 를 "청첩장을 직접 전해드릴게요. 아래 정보가 맞는지만 확인해 주세요." 로
   - `[맞아요, 계속]` 은 `onNext()` 를 호출 (하단 고정 "다음" 버튼과 같은 동작이라
     중복이면 생략 가능 — 실제로 붙여보고 결정할 것)

2. **`DeliveryForm` 에서 prop 전달**
   `invite?.name` 이 있고 `useInvitePhone` 이 true 인 경우에만 확인 모드가 되게 한다.
   (번호를 직접 입력하기로 한 뒤에는 확인 카드가 어색하다)

3. **문구**
   - 이름은 관리자가 명단에 입력한 값이라 **틀릴 수 있다.** `[정보 수정]` 이 눈에 띄어야 한다
   - "확인됨 ✓" 은 유지 — 하객이 자기 번호가 이미 있다는 걸 알아야 안심한다

## 절대 깨뜨리면 안 되는 것

- **전체 전화번호를 화면에 내리지 않는다.** 마스킹만. 실제 번호는 서버가 토큰으로
  채운다. E2E 가 `/010-\d{3,4}-\d{4}/` 로 감시 중이다 (`tests/e2e/db-flows.spec.ts`)
- **`[정보 수정]`(다른 번호 입력)을 눌러도 `inviteToken` 은 계속 전송한다.**
  예전에 여기서 토큰까지 지워 명단 연결(`group_member_id`)이 끊기는 결함이 있었다
  (결함 ①). 지금은 `useInvitePhone` 만 false 로 바뀌고 토큰은 그대로 간다 —
  이 성질을 깨지 말 것 (`docs/GROUP_PERSONAL_ORDER.md`)
- **초대가 없는 진입(`/delivery`)은 화면이 하나도 바뀌면 안 된다**
- 같은 폼을 그룹 링크(`/delivery/group/<slug>?i=`)도 쓴다 — **두 경로 모두 확인**
- 초대 해석 실패·타그룹 토큰일 때 뜨는 안내(`InviteNotice`)와 겹쳐 보이지 않게
