# 개인정보 보관·파기 운영 절차

적용 안내 버전: 2026-10-14. 예식: 2026-10-18 11:00 한국시간.

## 보관 대상과 기한

연락처·배송지·신청 명단·동반자 이름·참석/식사·체크인 정보의 기한은 예식 후 30일인 **2026-11-17 11:00 한국시간**이다. 기한 이후 수집·수정과 하객의 명단·배송 상세 조회를 차단한다. DB 파기는 관리자가 대상을 확인한 뒤 실행한다. 확인이 지연되면 관리자만 처리할 수 있는 상태로 남는다.

사진 파일, 사진의 한마디, 축하 글, 후기와 답글은 기념용으로 보존한다. 파기 시 작성자 표시를 ‘하객’으로 바꾸고 연락처·배송지·운영 명단 연결을 없앤다. 비공개 글과 숨김 사진은 계속 비공개다. 참석 신청의 메모도 비공개 기록으로 보존한다. 사진·본문 안에 포함된 개인정보까지 자동 식별하거나 지우지는 않는다.

## 본인 확인 및 접근 관리

- 하객의 신청 내역 확인, 참석 신청·수정, 공용 QR 예약 조회·체크인은 전체 전화번호로 받은 문자 인증을 사용한다. 기존 개인 초대·관리·입장 링크는 충분한 길이의 무작위 토큰을 사용한다. 링크를 전달받은 사람은 해당 권한을 행사할 수 있으므로 공유하지 않는다.
- 인증번호는 5분, 최대 5회 입력으로 제한한다. 성공한 코드는 재사용할 수 없다. 확인 권한은 용도·대상에 묶어 10분만 유지하고, 참석 제출 권한은 한 번만 쓴다. 번호/성함 변경 시 연결된 권한을 철회한다. 실제 코드는 저장하지 않는다.
- 관리자 로그인은 서버 세션을 사용하며 파기는 비밀번호 재확인이 필요하다. 공유 관리자 비밀번호이므로 기록은 개인별 담당자가 아닌 세션 식별 값이다.
- 관리자 조회·변경·내려받기 요청의 인증 허용/거절을 기록한다. 개인정보 테이블의 실제 추가·수정·삭제도 DB에서 별도로 기록한다. 요청 허용은 작업 성공을 뜻하지 않는다. 번호·배송지·본문·비밀번호·원본 토큰을 접근 기록에 남기지 않는다.
- 접근 이력은 최근 30일을 보관한다. DB의 `privacy-security-cleanup` 작업이 만료된 인증 권한·세션과 오래된 접근 기록을 매일 정리한다. Supabase Cron에서 작업과 실행 결과를 확인한다. 작업 실패 시 관리자에게 자동 알림이 가는 기능은 없다.

## DB 파기

1. 관리자 → 개인정보에서 기한, 삭제 대상 수, 보존 대상 수를 확인한다. 대상을 다시 불러온다.
2. 관리자 비밀번호, ‘개인정보 파기’ 확인 문구와 외부 사본 안내 확인을 입력한다. 기한 전에는 실행할 수 없다.
3. 서버는 확인한 대상과 현재 대상이 같은지 검증한다. 다르면 삭제하지 않고 다시 확인하도록 한다. 기록 보존·사진 작성자 제거·운영 명단 삭제를 한 DB 트랜잭션에서 처리한다. 실패하면 전체를 되돌린다.
4. 그룹 명단, 배송 신청 및 신청자, 참석 신청, 체크인, 대기 신청, 동반자, 알림 대기열, 초대/관리/복구/인증 토큰과 확인 기록을 지운다. 관리자 세션도 종료한다.
5. 다시 로그인해 파기 확인 번호·시간·건수를 확인한다. 사진은 하객스냅, 분리 보존한 글·배송 사진은 개인정보 → 보존 기록에서 확인한다.
6. 아래 외부 사본까지 실제 처리·만료를 확인한 뒤 완료 표시한다. DB 파기 완료와 외부 사본 완료는 별도 상태다. 이미 완료된 DB 파기를 다시 요청해도 같은 확인 결과만 반환한다.

## 외부 사본

- **로컬 파일:** 프로젝트 `backups/`의 기존 평문 JSON, 내려받은 명단·CSV·달력·스크린샷, 휴대폰·컴퓨터와 동기화/백업 사본, 휴지통을 확인해 운영 개인정보 사본을 삭제한다. 원래 연락처 앱의 주소록을 시스템이 자동 수정하거나 삭제하지는 않는다. 청첩장 운영을 위해 따로 만든 주소록 사본은 직접 확인한다.
- **Supabase:** 현재 플랜의 백업/PITR 보관 기간을 대시보드에서 확인한다. 임의 복구로 개인정보가 되살아나지 않도록 제한한다. 즉시 개별 삭제가 불가능하면 마지막 개인정보 포함 백업의 만료 시점을 기록하고 만료된 뒤 완료 표시한다. 공급자 백업과 수동 덤프를 구분한다.
- **솔라피:** 수신번호·문자 발송 내용·내려받은 발송 기록의 삭제 가능 범위와 의무 보관 기간을 서비스에서 확인한다. 필요한 삭제 요청을 하고 결과/만료를 확인한다. 이 앱의 DB 파기만으로 솔라피 기록은 삭제되지 않는다.
- **텔레그램·카카오:** 이름·배송 장소·관리 링크가 담긴 관리자 알림과 대화 사본을 확인해 서비스가 지원하는 방식으로 삭제한다. 다른 기기의 알림·내려받은 파일도 처리한다.
- 운영 서비스 로그나 별도로 만든 내보내기에 개인정보가 포함됐다면 해당 사본도 점검한다. 완료 확인의 근거는 번호/배송지 원문 없이 파기 확인 번호와 함께 운영자가 별도 보관한다.

## 백업과 복원

새 백업은 AES-256-GCM으로 암호화한 `.json.enc`만 생성한다. `BACKUP_ENCRYPTION_KEY`에 **별도로 생성한 32바이트 난수의 base64 값**을 설정해야 한다. 키는 백업과 다른 비밀번호 관리자 등에 보관한다. 키가 없으면 백업·복원을 중단한다. 키를 잃으면 복원할 수 없다. 기존 평문 백업은 자동 변환되거나 삭제되지 않으므로 위 절차로 별도 처리한다.

`npm run backup`은 파기 기한이 지난 미파기 DB의 새 사본 생성을 거절한다. `npm run restore -- backups/<시각> [테이블 목록]`은 모든 파일의 인증·복호화를 먼저 검증한다. 인증/세션/파기 상태는 복원하지 않고, 기한 이후 운영 개인정보 테이블 복원도 거절한다. 기한 이후 사진 복원에서는 작성자 이름을 제거한다. Supabase 전체 백업 복원은 이 스크립트의 보호를 우회하므로, 운영 서비스와 분리한 복구 환경에서 개인정보 파기를 다시 수행한 뒤 연결해야 한다.

## 조회·정정·삭제 요청

신랑·신부가 기존 초대 경로 또는 등록 번호로 본인을 확인하고, 요청자가 알지 못하는 번호·배송지를 답변에 노출하지 않는다. 명단과 신청자·배송·참석·대기 기록을 함께 확인해 정정/삭제한다. 사진·글 삭제 요청은 보존 기록과 사진 저장소·NAS 사본까지 별도 처리한다. 다른 사람의 사진이나 개인정보가 포함된 요청은 내용을 확인한 뒤 공개 범위/삭제를 처리한다. 처리 확인에는 개인정보 원문 대신 요청 시각, 처리 범위와 결과를 남긴다.

## 배포 순서

1. `20261013161559_privacy_controls.sql`을 적용한다. 운영 명단을 삭제하지 않는 추가 마이그레이션이다.
2. 새 앱을 배포하고 문자 인증 경로, 관리자 개인정보 화면, 기존 초대·사진 흐름을 확인한다.
3. 새 앱이 운영에 표시된 뒤 `20261013164805_private_guest_verification.sql`로 기존 익명 `verify_guest_v2` 실행 권한을 회수한다. 이 순서를 바꾸면 기존 앱의 본인 확인이 먼저 중단된다.
4. 익명 접근 거절, 서비스 역할 실행 가능, 기한 설정과 Cron 실행을 확인한다. 시험에는 운영 SMS 발송·개인정보 파기를 사용하지 않는다.
