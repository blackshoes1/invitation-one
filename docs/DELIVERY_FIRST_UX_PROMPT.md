# 개발 프롬프트: 처음 방문해도 쉬운 청첩장 배송 신청

저장소: blackshoes1/invitation-one. 최신 main과 AGENTS.md를 확인하고 별도 브랜치에서 구현한다.

## 목표

개인 초대 링크를 받은 하객이 첫 화면에서 ‘청첩장 받을 일정 정하기’를 바로 발견하고, 결혼식 참석 응답 없이도 신청을 완료할 수 있게 한다. 그룹 소속은 유지하되 보조 정보로 표시한다. 쇼핑몰 콘셉트의 친근함은 유지하면서 설명과 중복 확인을 줄인다.

## 화면 요구사항

1. 개인 링크 첫 화면
   - 초대받은 이름·마스킹 연락처와 소속 그룹을 간결하게 표시한다. 원본 연락처는 브라우저에 내려주지 않는다.
   - 큰 기본 버튼은 ‘청첩장 받을 일정 정하기’ 하나로 한다. 320×568, 390×844 화면에서 스크롤 없이 보여야 한다.
   - ‘지역과 날짜·시간을 고르면 돼요. 결혼식 참석 응답과는 별개예요.’라고 설명한다.
   - ‘축하 한마디만 남기기’, ‘모바일 청첩장 보기’, 기존 신청 확인은 보조 동작으로 제공한다.
   - 참석 응답·공유 동의·모임 명단·모임 일정은 기본 접힌 보조 영역에 둔다. 응답 저장은 배송 신청 완료로 오해하지 않게 구별한다.
   - 의미 없는 ‘메뉴로 돌아가기’ 대신 ‘다른 방법으로 받기’를 사용한다.

2. 신청 과정
   - 4단계: 받는 지역 → 날짜·시간 → 전달 방법·요청 → 최종 확인.
   - 초대로 확인된 이름·번호는 별도의 필수 확인 단계를 만들지 않는다. 연락처 누락·일반 방문은 첫 단계에서 필요한 정보만 입력한다.
   - 날짜와 시간 선택을 한 단계에서 처리한다. 날짜 변경 시 불가능한 시간은 해제한다.
   - 신랑·신부·함께 방문 선택과 선택 입력인 요청사항은 같은 단계에 둔다. 임의로 방문자를 확정하지 않는다.
   - 확인 화면은 마스킹 연락처·지역·일정·방문자·요청사항을 보여주며, 이름·연락처를 수정할 수 있게 한다. 수정해도 개인 초대 토큰은 유지한다.
   - 진행 표시와 실제 단계는 같은 정의에서 계산한다. 단계 전환과 버튼을 동시에 갱신하고 연타·중복 전송을 방지한다.
   - 오류는 현재 입력 가까이에 표시하고 다음 단계로 넘어가지 않는다. 단계 이동 시 새 제목으로 포커스를 옮긴다.

3. 회귀 방지
   - 개인 주문과 그룹 주문의 구분, 기존 주문 합류·제안 수락·마음배송 전환·마감 상태·신청 관리 기능을 유지한다.
   - 다른 초대 간 임시 입력 분리, 본인이 아닐 때 초기화, 기존 초대 토큰 검증·명단 연결·원자적 저장을 유지한다.
   - 모임 공유는 명시적 선택과 저장이 있을 때만 적용한다. 화면을 보거나 배송을 신청하는 것만으로 참석·공유 정보를 저장하지 않는다.
   - UI 개선을 위해 운영 DB 구조나 기존 API 계약을 변경하지 않는다.

## 검증 및 완료 조건

- 모바일 320×568·390×844 및 데스크톱에서 첫 CTA 노출, 가로 넘침, 버튼 겹침을 검사한다.
- 개인 링크·일반 방문·그룹 없는 초대·잘못된 링크·연락처 누락·마감 상태를 검증한다.
- 4단계 정상 흐름, 단계별 오류, 최종 연락처 수정, 날짜 변경, 빠른 연타, 뒤로 이동, 새로고침 초안 복원, 그룹 합류 흐름을 회귀 테스트한다.
- 제출 전까지 주문·참석 응답을 저장하지 않는지 검사한다. 실제 운영 주문·문자 발송으로 테스트하지 않는다.
- lint, TypeScript, 단위 테스트, 빌드 및 관련 E2E를 실행하고 새 PR에 결과를 기록한다.
- 완료 시 프롬프트 파일 링크, PR 링크, 검증 결과와 남은 제한을 제공한다. 운영 배포는 이번 UI 구현과 분리하며 권한 문제를 우회하지 않는다.
