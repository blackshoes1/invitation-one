# 배포 리전 — 함수를 DB 옆에 둔다

작성: 2026-09-09 · 예식 2026-10-18

## 왜 도쿄인가

`vercel.json` 의 `"regions": ["hnd1"]` (도쿄). **JSON 에 주석을 못 달아서** 이유를
여기 적는다.

Supabase 프로젝트는 **`ap-northeast-1`(도쿄)** 에 있다. 그런데 Vercel 함수는
설정이 없어 기본값인 **`iad1`(미국 동부)** 에서 돌고 있었다. 관리자는 한국에 있다.
요청 하나가 지구를 두 바퀴 돈 셈이다.

관리자 화면이 느린 게 이것 때문이었다. 관리자 API 는 요청당 DB 왕복이 여러 번이라
거리가 그대로 곱해진다:

| 동작 | HTTP 왕복 | DB 왕복 |
|---|---|---|
| 명단 추가 | 2 | 6 |
| 주문 생성 | 2 | 7 |
| 그룹 생성·이름변경·제안 저장 | 2 | 6 |
| 연락처 저장 | 1 | 3 |

DB 왕복이 많은 이유 둘:
- `checkAdmin()` 이 **모든** 관리자 요청에서 `admin_sessions` 를 조회한다
  (세션을 즉시 철회할 수 있게 하는 설계라 그대로 둔다 — 함수가 DB 옆에 있으면 몇 ms다)
- 뮤테이션 뒤 목록을 다시 불러온다

거리별 대략치 (주문 생성 = HTTP 2 + DB 7 기준):

| 함수 위치 | 브라우저↔함수 ×2 | 함수↔DB ×7 | 합계 |
|---|---|---|---|
| `iad1` 미국 동부 (예전) | ~400ms | ~1,190ms | **~1.6초** |
| `icn1` 서울 | ~20ms | ~245ms | ~0.27초 |
| **`hnd1` 도쿄 (지금)** | ~60ms | ~14ms | **~0.08초** |

**서울이 아니라 도쿄인 이유**: 왕복이 HTTP 2번보다 DB 7번이 훨씬 많다. 사용자 옆보다
**DB 옆**에 붙이는 쪽이 크게 이긴다. 한국↔도쿄는 어차피 30ms 남짓이다.

데이터 양은 원인이 아니었다 — 그룹 17 · 명단 53 · 참여자 32 규모라 쿼리 자체는
밀리초다. 느린 건 **거리**였다.

## 옮길 일이 생기면

Supabase 프로젝트를 다른 리전으로 옮기면 **이 값도 같이 바꿔야 한다.** 둘이
어긋나는 순간 위 표의 맨 윗줄로 돌아간다.

## `preferredRegion` 은 쓰지 않는다

Next 의 route segment config `preferredRegion` 은 이 버전에서 **deprecated** 다
(`node_modules/next/dist/docs/.../preferredRegion.md`). 리전은 플랫폼 설정인
`vercel.json` 으로 지정한다.

## Hobby 플랜

단일 리전만 지정할 수 있는데, 지금 필요한 건 그게 전부다.

## 남은 지연

- **콜드 스타트**: 관리자 페이지는 가끔 쓰므로 첫 요청이 거의 항상 콜드다.
  Hobby 에서 이걸 없앨 방법은 마땅치 않다.
- **왕복 횟수 자체**: 리전 정렬로 한 번의 비용이 싸졌을 뿐 횟수는 그대로다.
  더 줄이려면 뮤테이션 뒤 전체 재조회를 없애고(POST 응답을 그대로 쓰기) 낙관적
  표시를 붙이는 쪽이다.
