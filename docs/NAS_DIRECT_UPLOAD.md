# NAS 직접 사진 업로드

## 개발 완료와 실제 연결은 별개

운영 청첩장은 `GUEST_PHOTO_STORAGE=nas`로 NAS 직접 업로드를 사용합니다. 2026-10-16 새 공개 경로는 `https://bokbok9.synology.me:1018/photos/snap/…`입니다. 기존 HTTPS 연결에 사진 전용 프록시를 추가해 Tailscale Funnel의 중계 구간을 거치지 않습니다. 이전 `https://bokbok9.tail8b977f.ts.net` 사진 주소도 유지합니다. NAS가 꺼지거나 연결이 실패하면 오류를 표시하며 Supabase에 대신 저장하지 않습니다.

`https://bokbok9.synology.me:1018/`의 루트는 DSM 관리 화면입니다. `/photos/snap/`과 `/invitation-photos-health`만 사진 서비스의 `127.0.0.1:18080`으로 연결했습니다. 기존 DSM 경로와 포트 전달 설정은 유지합니다. 아래 10443 포트 설정은 다른 환경에 별도 주소를 설치할 때의 예시입니다.

운영 프록시 원본은 `ops/nas-upload/dsm.invitation-photos.conf`이며 NAS의 `/usr/local/etc/nginx/conf.d/dsm.invitation-photos.conf`에 설치합니다. `proxy-test.conf`로 사진 프록시만 독립적인 Nginx 환경에서 문법 검증할 수 있습니다. DSM의 기존 Nginx가 이 파일을 include하며, 적용 시 graceful reload 후 공개 상태 응답과 DSM 접속을 확인합니다. DSM 업데이트 후에도 이 파일과 경로가 유지되는지 확인하세요.

`ops/nas-upload/public-origins.json`은 기존 운영 origin을 새 공개 origin으로 매핑합니다. 다른 NAS 설정은 바꾸지 않습니다. `NAS_PHOTO_PUBLIC_BASE_URL`을 명시하면 매핑보다 우선하므로 이전 Funnel origin으로 롤백할 수 있습니다. 웹 배포 시 새 주소와 기존 주소 모두 CSP·이미지 허용 목록에 포함됩니다. 기존 DB의 사진 URL은 변경하지 않습니다.

공개 경로 검사는 `curl --fail https://bokbok9.synology.me:1018/invitation-photos-health`로 수행합니다. 인증서를 무시하는 옵션을 사용하지 않습니다. `/photos/snap/`의 PUT·HEAD·DELETE에는 기존과 같은 서명 권한이 필요하고, HTTPS 이외의 사진 경로는 차단합니다.

## 데이터 흐름

1. 청첩장 서버가 현재 업로드 세션·횟수·파일 크기를 확인하고, 파일 경로·해시·작성자에 묶인 30분짜리 권한을 발급합니다.
2. 브라우저가 공개 사진 URL의 `?admission=1`에 작은 인증 GET으로 차례를 요청합니다. `202`일 때는 본문을 보내지 않고 `Retry-After` 뒤에 다시 확인합니다. `200`의 전송 허가(lease)를 받은 두 명만 원본을 NAS로 직접 PUT 전송합니다. 사진 본문은 Vercel과 Supabase Storage를 통과하지 않습니다.
3. NAS는 서명·크기·실제 파일 형식·SHA-256을 검증하고 파일을 저장한 후 서명된 완료 확인서를 반환합니다.
4. 청첩장 서버는 확인서와 NAS 파일 존재·해시를 확인하고 Supabase DB에 사진 주소·작성자·축하글만 저장합니다. 같은 확인서를 다시 처리해도 기존 ID를 재사용하며 숨김 상태를 덮어쓰지 않습니다.
5. 앨범은 NAS 사진을 직접 표시합니다. 기존 Supabase 사진도 계속 표시됩니다.

브라우저에서 선택한 사진 파일을 압축·리사이즈·프레임 적용 없이 그대로 저장합니다. EXIF 등 메타데이터도 유지됩니다. 한 장당 20MB까지 지원합니다. 기기나 사진 선택기가 전달 전에 변환한 파일까지 복원하는 기능은 아닙니다. HEIC는 브라우저에 따라 미리보기가 표시되지 않을 수 있지만 원본 업로드는 가능합니다.

## NAS 설치

1. Container Manager를 설치하고 `ops/nas-upload` 전체를 `/volume1/docker/invitation-nas-upload`에 복사합니다.
2. 사진 폴더 `/volume1/photo/wedding-direct`를 만듭니다. 실행할 NAS 사용자에게 읽기·쓰기 권한을 줍니다.
3. `env.example`을 `.env`로 복사합니다. `id 사용자명`으로 확인한 UID/GID를 입력하고, 필요하면 사진 폴더 경로를 바꿉니다.
4. `openssl rand -hex 32` 등으로 무작위 비밀키를 생성해 `.env`의 `NAS_PHOTO_SECRET`에 입력합니다. 같은 값을 나중에 Vercel **서버 전용** 변수에 넣습니다. DSM 비밀번호나 Supabase 서비스 키를 사용하지 마세요. 키를 GitHub나 채팅에 게시하지 않습니다.
5. `ALLOWED_ORIGINS=https://kkachi.vercel.app`을 설정합니다. 다른 실제 청첩장 도메인이 있으면 쉼표로 추가합니다. 와일드카드는 지원하지 않습니다.
6. Container Manager 프로젝트로 `compose.yaml`을 실행하거나 NAS 터미널에서 실행합니다.

```sh
cd /volume1/docker/invitation-nas-upload
docker compose up -d
docker compose ps
docker compose logs --tail=50 nas-photos
curl --fail http://127.0.0.1:18080/health
```

health 응답은 `{"service":"invitation-nas-photos","version":2}`입니다. 이 검사는 서비스와 폴더 접근만 확인하며 실제 저장 검증은 아래 사진 테스트가 필요합니다.

## HTTPS 연결

DSM 역방향 프록시에서 별도 규칙을 만듭니다. DSM 버전에 따라 로그인 포털의 고급 설정 또는 응용 프로그램 포털에 있습니다.

| 항목 | 예시 |
| --- | --- |
| 외부 프로토콜 | HTTPS |
| 외부 호스트 | bokbok9.synology.me |
| 외부 포트 | 10443 (사용 가능 여부 확인) |
| 내부 프로토콜 | HTTP |
| 내부 호스트 | 127.0.0.1 |
| 내부 포트 | 18080 |

유효한 `bokbok9.synology.me` TLS 인증서를 이 규칙에 지정합니다. 공유기를 사용한다면 외부 TCP 10443을 NAS의 같은 포트로 연결합니다. 내부 HTTP 18080은 공개하지 않습니다. 기존 DSM 1018 포트 설정은 변경하지 않습니다. 역방향 프록시는 PUT·HEAD·DELETE·OPTIONS와 Authorization 헤더를 전달하고, 최소 20MB 요청 본문과 300초 전송 시간을 허용해야 합니다. TLS 검사 무시 옵션으로 우회하지 마세요.

휴대폰의 Wi-Fi를 끄고 `https://bokbok9.synology.me:10443/health`에서 서비스 JSON이 나오는지 확인합니다. DSM 로그인 화면이나 HTML이 나오면 업로드 서비스로 연결된 것이 아닙니다.

## 청첩장 설정과 전환

NAS 확인 후 Vercel 서버 환경변수에 아래를 설정하고 재배포합니다. 주소는 경로 없는 HTTPS origin으로 설정합니다.

```text
GUEST_PHOTO_STORAGE=nas
NAS_PHOTO_BASE_URL=https://bokbok9.synology.me:10443
NAS_PHOTO_SECRET=NAS의 .env에 설정한 동일한 무작위 키
```

`NEXT_PUBLIC_` 접두사를 붙이지 않습니다. 키는 서버와 NAS만 보관합니다. 주소는 업로드 권한 응답으로 브라우저에 전달됩니다. CSP와 이미지 허용 목록에도 적용되므로 변수 변경 후 재배포가 필요합니다.

먼저 Preview에서 테스트한다면 해당 Preview의 정확한 origin을 NAS `ALLOWED_ORIGINS`에 추가하고 컨테이너를 다시 생성합니다. 검증 후 운영 환경에 적용합니다.

## 실제 연결 검증 순서

- 사진 한 장 업로드: 브라우저 네트워크에서 NAS로 PUT이 전송되고 `/api/guest-photos/direct`에는 JSON만 전송되는지 확인합니다.
- NAS의 `snap/UUID.jpg` 등을 실제로 열고 앨범 표시를 확인합니다. Supabase Storage에 새 파일이 생성되지 않아야 합니다.
- 관리자 숨김/공개를 확인합니다. 숨김은 앨범 목록에서만 제외하며 URL을 이미 아는 사람의 접근까지 차단하지 않습니다. 기존 공개 사진 정책과 같습니다.
- 관리자 삭제 시 NAS 파일이 삭제되고 주소가 410으로 응답하는지 확인합니다. 삭제 표식은 `deleted` 폴더에 남아 만료 전 업로드 권한 재사용을 차단합니다.
- NAS 서비스를 중지한 상태에서 새 업로드가 실패하고 Supabase로 우회 저장되지 않는지 확인한 뒤 서비스를 다시 시작합니다.

## 장애·보관

NAS는 새 사진의 주 저장소입니다. 전원·인터넷·디스크 장애 시 새 업로드와 NAS 사진 보기가 중단됩니다. 별도 NAS 백업은 사용자가 설정해야 하며, 앞서 만든 Supabase→NAS 복사 프로그램과는 용도가 다릅니다.

메타데이터 등록만 실패하면 동일 확인서로 최대 5번 자동 시도합니다. 끝내 실패하면 사진 파일만 NAS에 남을 수 있습니다. 이 파일은 자동으로 지우지 않습니다. 관리자 삭제 중 DB 장애가 나면 재시도하여 행 삭제를 완료하세요. 삭제 표식 폴더를 임의로 지우지 마세요.

기존 Supabase 사진은 이전하지 않습니다. 롤백은 `GUEST_PHOTO_STORAGE=supabase` 후 재배포합니다. 이미 등록된 NAS 사진을 표시·삭제하려면 NAS 서비스와 URL/비밀키 설정은 유지해야 합니다. NAS 주소 변경은 기존 DB 사진 주소 이전 작업도 필요합니다.

자동 검증: `npm test`, `node --test ops/nas-upload/server.test.mjs`. CI는 실제 운영 데이터 대신 임시 폴더와 공식 Node 컨테이너로 업로드·검증·중복 확인·삭제 후 재업로드 차단을 검증합니다. 실제 NAS 접속과 업로드는 위 절차를 마쳐야 검증 완료입니다.

## 여러 하객의 동시 업로드와 재시도

- NAS는 사진 업로드를 **동시에 2건** 처리합니다. 새 브라우저는 최대 100명 규모의 대기를 작은 요청으로 등록하고, 응답 후 연결을 닫습니다. 전송 허가가 없으면 원본 본문을 보내지 않아 공개 중계 경로에 수십 개의 큰 요청을 쌓지 않습니다.
- 먼저 도착한 순서로 전송 허가를 내줍니다. 허가를 받은 후 **45초** 동안 전송을 시작하지 않으면 자리를 반환합니다. 대기자는 1~5초 간격과 무작위 지연으로 확인합니다. 맨 앞 두 대기자는 작은 확인 요청을 최대 15초 유지해 자리가 나자마자 허가를 받습니다. **120초** 이상 확인하지 않은 대기는 정리합니다. 서버 재시작 후에도 같은 사진 ID로 다시 대기할 수 있습니다. 구버전 브라우저는 기존의 45초 PUT 대기 방식으로 호환됩니다.
- 새 브라우저는 한 장당 대기·복구를 **최대 25분**, 각 전송은 최대 5분으로 제한합니다. `408·425·429·5xx`와 연결 오류는 원본을 바로 재전송하지 않고 저장 상태와 차례부터 확인합니다. 일시 장애가 계속되면 실패한 사진을 화면에 남깁니다.
- 같은 URL·권한·사진 바이트를 재사용합니다. 저장 후 응답만 끊긴 경우 NAS에서 크기·SHA-256이 일치하는 파일을 확인하고 새 완료 확인서를 돌려주므로 본문 재전송과 중복 저장을 피합니다. 완료 확인은 같은 확인서로 최대 5번, 총 90초 안에서 재시도합니다. 권한 요청은 최대 3번 재시도합니다.
- `400·401·403·404·409·410·413` 등 사진·권한 문제와 청첩장 API의 실제 횟수 제한은 자동 반복하지 않습니다. NAS 장애 시 Supabase로 우회 저장하지 않습니다.
- NAS 모드의 업로드 권한 요청 한도는 세션당 **10분 30회**, 같은 IP당 **10분 3,000회**입니다. 공용 Wi-Fi에서 100개 세션이 각자 한도를 사용할 수 있는 범위입니다. 업로드 토큰 갱신은 같은 IP당 10분 300회, 완료 확인은 세션당 10분 180회로 제한합니다. 성공 장수가 아닌 요청 횟수이며, 기존 Supabase 파일 업로드 모드의 IP 한도는 그대로입니다.
- 화면에 전송·자동 재시도·앨범 등록 상태를 표시합니다. 브라우저를 닫거나 휴대폰이 페이지 실행을 중단하면 자동 업로드도 이어지지 않으므로 완료될 때까지 화면을 열어두어야 합니다.

로컬 자동 검증은 **50개 세션이 각 10장씩, 500개 파일을 모두 원본 그대로 저장**, 대기 중 본문 미전송, 전송 허가 만료·반환, 저장 응답 복구, 삭제 재사용 차단과 구버전 호환을 확인합니다. 공개 인터넷 시험에서는 사설 Tailscale DNS를 피하고 공개 DNS IP에 TLS 호스트 검증을 유지한 채 연결해야 합니다. 한 PC의 50개 세션 시험은 서로 다른 통신사와 휴대폰 50대 시험을 대신하지 않습니다. 느린 회선이나 장시간 장애가 상한을 넘으면 실패 안내와 미완료 사진을 남깁니다.

적용하려면 **청첩장 웹 배포와 NAS 프로그램 업데이트가 모두 필요**합니다. 아래 NAS 업데이트 명령은 사용자가 적용 시 실행하는 절차이며 로컬 코드 수정만으로 운영 설정이 바뀌지 않습니다.


## 기존 NAS 프로그램 업데이트 (원본 20MB 지원)

웹 배포와 별도로 NAS SSH에서 아래를 실행합니다. 기존 `.env`와 사진 파일은 유지됩니다.

```sh
cd /volume1/docker/invitation-one
git pull --ff-only origin main
cd ops/nas-upload
sudo docker compose up -d --force-recreate nas-photos
curl --fail http://127.0.0.1:18080/health
```

원본 선택 파일과 NAS 파일의 SHA-256이 같은지 비교하면 바이트 단위 보존을 확인할 수 있습니다. 이전에 압축해서 저장한 사진은 원본으로 되돌릴 수 없습니다.
